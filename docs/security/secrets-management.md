# Production secrets management

How Hermes v2 gets configuration and secrets into the production container on
ROMEO without ever putting them in git, a Docker image, the frontend, or logs.
Written ahead of the Binance integration so key/secret handling is decided
once, deliberately, rather than improvised when trading code lands.

## 1. Architecture

```
ROMEO host
  /opt/hermes-v2/.env          (gitignored, chmod 600, real values)
  /opt/hermes-v2/compose.yaml  (from this repo, no secrets inside it)
       │
       │  docker compose reads .env twice, for two different purposes:
       │  1. variable substitution inside compose.yaml itself (${POSTGRES_USER}, ...)
       │  2. env_file: .env on the hermes-v2 service → injected into the
       │     container's process environment at container start
       ▼
  hermes-v2 container (image pulled from GHCR, built with no secrets baked in)
       │  os.environ.get("GOOGLE_CLIENT_SECRET"), etc. — read once, at the
       │  point of use, never logged, never echoed to a response
       ▼
  FastAPI process
```

Deploy stays pull-based, exactly as documented in `SECURITY_AUDIT.md` §2: CI
builds and publishes the image to GHCR on merge to `main`; a systemd timer on
ROMEO polls GHCR and redeploys on digest change. **GitHub Actions never holds
a ROMEO credential and never sees a production secret** — no workflow in this
repo reads `.env` or references a Binance/Google/Postgres secret. That
property doesn't change with this PR.

`.env` never enters the Docker build context (`.dockerignore` excludes
`.env*`) and the `Dockerfile` never `COPY`s or declares an `ARG`/`ENV` for
any secret — the image is identical whether it ends up running in dev, CI, or
ROMEO. Secrets exist only in the container's runtime environment, supplied by
`compose.yaml`'s `env_file: .env` at `docker compose up`, not before.

### Why plain `env_file`, not Compose `secrets:` or a vault

Compose (even without Swarm) supports file-based `secrets:`, which mount each
secret as a file under `/run/secrets/<name>` instead of an environment
variable. That was considered and rejected for now:

- It requires every place that currently does
  `os.environ.get("GOOGLE_CLIENT_SECRET")` to instead read a file path — a
  code change per secret, not a config change, which cuts against "rotate
  without touching code."
- Its main advantage over `env_file` is hiding values from `docker inspect`
  output. On ROMEO, anyone who can run `docker inspect` already has root (or
  the ability to read `/opt/hermes-v2/.env` directly) — the marginal
  protection is close to zero at this trust level (single operator, single
  server).
- No secrets manager (Vault, AWS Secrets Manager, etc.) exists anywhere in
  this project today, and introducing one is out of scope per the task that
  produced this PR — it would be new infrastructure to run and secure, for a
  single-server deployment that doesn't need it yet.

`env_file` + a gitignored, `chmod 600` `.env` on the host is the simplest
mechanism that satisfies every hard requirement below. Revisit this decision
specifically if Hermes ever moves off a single trusted host (already flagged
in `SECURITY_AUDIT.md` §22 as a "not necessarily before Binance" item).

## 2. Files on ROMEO, and what's in git

| File | In git? | Contains secrets? | Notes |
|---|---|---|---|
| `/opt/hermes-v2/.env` | **No** — gitignored (`.env`, `.env.*` in `.gitignore`) | Yes | The only file with real values. Must be `chmod 600`, owned by the deploy user. Created once by hand on ROMEO; never generated by CI, never round-tripped through git. |
| `/opt/hermes-v2/compose.yaml` | Yes — this repo's `compose.yaml` | No | References variables (`${POSTGRES_USER}`, `env_file: .env`) but holds no values itself. Safe to keep in sync with git on ROMEO (e.g. `git pull` or copy on deploy). |
| `.env.example` (this repo) | Yes | No — placeholders only | Template a ROMEO operator diffs their real `.env` against to catch drift (already recommended in `SECURITY_AUDIT.md` §21). |
| `.env.dev.example` (this repo) | Yes | No — placeholders only | Same idea, for local dev. |
| `.dockerignore` | Yes | No | Excludes `.env`, `.env.*`, `*.key`, `*.pem`, `secret*`, `credentials*` from the build context. |

`scripts/check-env-permissions.sh` (added in this PR) can be run directly on
ROMEO to verify `.env` is `600`:

```sh
./scripts/check-env-permissions.sh /opt/hermes-v2/.env
```

It exits non-zero with a `chmod` suggestion if the file is missing or more
permissive than `600`/`400`. This has to be run on ROMEO itself — nothing in
this sandbox has access to that host.

## 3. Config vs. secrets

Not everything the app reads from the environment is sensitive. Splitting
`.env.example`'s contents:

**Secrets (high sensitivity — leak has direct impact):**

| Variable | Used for |
|---|---|
| `GOOGLE_CLIENT_SECRET` | OAuth code exchange, server-side only |
| `POSTGRES_PASSWORD` (and the password embedded in `DATABASE_URL`) | Database authentication |
| `BINANCE_API_KEY` / `BINANCE_API_SECRET` | The one operator-level Binance key `cli.py`'s `binance_check()` diagnostic reads — see §7 |
| `HERMES_CREDENTIALS_ENCRYPTION_KEY` / `HERMES_CREDENTIALS_ENCRYPTION_KEY_PREVIOUS` | Encrypts every per-user Binance credential at rest — see §7 |

**Config (not secret, but still belongs only in `.env`, not hardcoded):**

`GOOGLE_CLIENT_ID`, `GOOGLE_REDIRECT_URI`, `HERMES_ADMIN_EMAIL`,
`HERMES_ALLOWED_ORIGINS`, `HERMES_ALLOWED_RETURN_URIS`,
`HERMES_DEFAULT_RETURN_URI`, `HERMES_COOKIE_SECURE`,
`HERMES_COOKIE_SAMESITE`, `HERMES_SESSION_TTL_SECONDS`,
`HERMES_TRUST_PROXY_HEADERS`, `POSTGRES_DB`, `POSTGRES_USER`.

These are per-deployment values, not credentials — safe to see, not safe to
assume are the same across dev/prod. `.env.example` documents every one with
a comment explaining what it controls (see `SECURITY_AUDIT.md` §9 for the
full inventory this table is derived from).

The frontend (`hermes_front_end`, a separate repo/container) reads exactly
one environment variable, `EXPO_PUBLIC_API_URL`, which is not sensitive by
design — it's baked into the public JS bundle regardless. It has no access to
`hermes_v2`'s `.env` at all: different repo, different container, different
build. There is structurally no path for a backend secret to reach the
frontend today, and none of this PR's changes create one.

## 4. Rotating a secret

No code change, no image rebuild, no git commit required for any secret in
the table above:

1. On ROMEO, edit `/opt/hermes-v2/.env` and update the one line.
2. Apply it:
   ```sh
   docker compose -f /opt/hermes-v2/compose.yaml up -d hermes-v2
   ```
   **Not `restart`** — `restart` reuses the container's already-materialized
   environment and will not pick up the new `.env` value. This is already
   documented as a known gotcha in `SECURITY_AUDIT.md` §16, carried forward
   here.
3. Verify the service came up healthy (`docker compose ps`, and for
   Google/DB-touching secrets, exercise the login flow or check
   `/health`).
4. If the secret is a Postgres password: update it in Postgres itself first
   (`ALTER USER ... PASSWORD ...`) in the same maintenance window, before or
   immediately after updating `.env` — the two must agree or the app can't
   connect.

This is also how `BINANCE_API_KEY`/`BINANCE_API_SECRET` will be rotated once
they exist: same file, same command, no different from any secret today.

## 5. Rollback

Two independent things can go wrong, with two independent rollbacks:

- **A bad app deploy** (new image version misbehaves): secrets live outside
  the image entirely, so rolling back to the previous image digest never
  touches `.env`. Re-point the systemd/compose deploy at the previous
  digest and `up -d` — no secret handling involved.
- **A bad secret rotation** (new value is wrong/revoked): edit `.env` back to
  the previous value and `up -d` again (step 2 above). Because `.env` is a
  plain file on the host, keeping a short-lived, permission-restricted
  backup copy before a rotation (e.g. `cp .env .env.bak-$(date +%s)` — this
  file must never be committed, and should be deleted once the rotation is
  confirmed good) is enough to make rollback a two-command operation. No
  automated backup tooling is being introduced for this — it's a manual
  step in the rotation runbook, matching the "simple, single-server" scope
  of this PR.

## 6. How Docker Compose consumes secrets

`compose.yaml`'s `hermes-v2` service:

```yaml
env_file:
  - .env
```

This injects every variable in `.env` into the container's process
environment, unmodified. `hermes_v2`'s code reads them the same way in every
environment — dev, CI test fixtures, and ROMEO all use
`os.environ.get("SOME_VAR")` — so there's exactly one code path for "how does
this app get configured," regardless of where it runs.

Separately, Compose auto-loads a file literally named `.env` sitting next to
`compose.yaml` for **its own** `${VARIABLE}` substitution inside the compose
file (used by the `postgres` service's `environment:` block and healthcheck).
Because both mechanisms point at the same `/opt/hermes-v2/.env`, one file
serves both purposes — no second copy of `POSTGRES_PASSWORD` to keep in sync.

Adding a brand-new secret (e.g. `BINANCE_API_KEY` when that work begins)
needs **zero changes to `compose.yaml`**: add the line to `.env` on ROMEO,
`up -d hermes-v2`, and any code that later reads
`os.environ.get("BINANCE_API_KEY")` sees it. The mechanism is already
future-proof for this — nothing in this PR needs to change when trading work
starts.

## 7. Binance trading (implemented, disabled by default)

**Update (`feature/binance-trading-integration-v1`):** the section below
was written when this repo had no Binance client at all. That's no longer
true — a full read+write client, order execution pipeline, and REST API
now exist (see `docs/architecture/trading.md`), but live execution stays
inert behind `TRADING_ENABLED=false` until an operator deliberately enables
it per that document's activation runbook. What follows is what's still
true, and what changed:

- Create the Binance API key with **withdrawals disabled** and an **IP
  allowlist restricted to ROMEO's egress IP** (Binance account-console
  settings, not a Hermes change) — already flagged in `SECURITY_AUDIT.md`
  §22 as the single most important prerequisite, and enforced by `hermes
  binance-check`'s permissions check.
- Set `BINANCE_API_KEY`/`BINANCE_API_SECRET` directly in ROMEO's `.env`
  following §4/§6 above — this remains the operator-level key
  `cli.py`'s `binance_check()` diagnostic reads, decoupled from what the
  trading routes read after the change below.
- **Update (multi-tenant trading):** the "never in the database" decision
  above was reversed once more than one real person needed to trade with
  their own Binance account. A single shared operator key can't express
  "many users, many distinct accounts," so each user now connects their
  own key/secret from the Settings UI; each is verified against Binance
  (`get_account_info()`, rejecting any key with withdrawals enabled)
  *before* it is ever written, then stored as `Fernet`/`MultiFernet`
  ciphertext (AES128-CBC + HMAC-SHA256, versioned/authenticated tokens)
  in `user_binance_credentials`, keyed by a new `.env`-only
  `HERMES_CREDENTIALS_ENCRYPTION_KEY` (generated once, never in git,
  same `chmod 600` handling as every secret in this document; missing =
  every credential read/write fails closed with a 503). `MultiFernet`
  was chosen specifically for built-in rotation: generate a new key,
  move the old value into a comma-separated
  `HERMES_CREDENTIALS_ENCRYPTION_KEY_PREVIOUS` (decrypt-only), restart —
  no bulk re-encryption pass required. Plaintext exists only for the
  duration of the connect request and of a later decrypt-to-call-Binance
  request; it is never logged and never returned in any response body
  (only `api_key_last4` and timestamps are). See
  `docs/architecture/multi-tenant-trading.md` for the full design.
- **Done:** structured audit logging exists (`audit_log` table, written by
  `OrderService` for every mutating trading action's outcome —
  success/rejected/failed, never a secret).
- **Done:** idempotency exists (two layers — see
  `docs/architecture/trading.md`).
- Directly verify, on ROMEO, the pre-existing production-config gaps this
  section originally flagged: `HERMES_ALLOWED_RETURN_URIS`,
  `HERMES_ALLOWED_ORIGINS`, `HERMES_COOKIE_SECURE`, `POSTGRES_PASSWORD`
  strength, and the backend container's port binding — all listed with
  exact commands in `SECURITY_AUDIT.md` §21. These should be closed before
  `TRADING_ENABLED` is ever set to `true`, since `HERMES_ALLOWED_ORIGINS`
  in particular is now also what `require_trusted_origin()` checks for
  every mutating trading request, not just CORS.
